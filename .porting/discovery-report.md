# Codebase Discovery Report: GoldenEye 007 Swift 6 / Metal 4 macOS Port

## Summary

The checkout contains the upstream `n64decomp/007` decompilation at commit `c4356466` (`james bond will return.`). It is a N64-only C and MIPS-assembly codebase with no macOS target, Swift target, host window layer, or graphics abstraction. The game builds N64 `Gfx` display lists on the CPU and submits them to RSP/RDP microcode; the highest-leverage direct-Metal seam is a host-side GBI/RDP interpreter at `rspGfxTaskStart`, while retaining as much gameplay and display-list production as can be made host-portable.

The external US ROM at `/Users/derek/Documents/GoldenEye 007 (USA).z64` matches `ge007.u.sha1` exactly. The repository asset extractor has been run successfully: 2,698 image payloads and approximately 15 MB of binary assets are now available locally (ignored by the upstream repository). No GPU traces or reference captures are available.

## Practical Porting Advice

- Preserve the decomp’s display-list producer semantics first. The master list is assembled in `src/game/lv.c::lvlRender`, finalized in `src/boss.c::bossMainloop`, and submitted by `src/game/rsp.c::rspGfxTaskStart`.
- Build a host target beside the ROM Makefile rather than replacing the N64 build. The existing Makefile remains useful for source/asset parity and ROM hash checks.
- Use a debug Swift 6/Xcode target with macOS 26+ and Metal 4. The host machine’s macOS/Xcode 27 environment satisfies the API availability requirement.
- The first useful native milestone should be a window, a Metal 4 clear, and a deterministic replay of a small static display list. This isolates the renderer from the full game loop.
- Next, add a CPU-side GBI interpreter that emits normalized draw packets. Keep texture conversion, matrix conversion, and combiner lowering independently testable.
- Use Metal 4 command buffers created from the device, one allocator per in-flight frame, argument tables instead of `set*Bytes`/per-encoder binding, and an explicit residency set. Use transient shared buffers for per-frame constants and private textures for steady-state resources.
- On Apple TBDR, prefer fewer render-pass boundaries. Depth and other throwaway attachments should use memoryless storage and `DontCare` stores when their contents are not consumed after the pass.
- Keep every temporary shortcut marked with `STUB(Mx)` and every hardcoded value annotated with its intended source/milestone.
- Enable Metal validation and Metal HUD early; implement resource labels/debug groups before optimizing.
- Use the verified ROM only as an external input. Do not add it to the repository or generated source control state.

## Risk Assessment

- **Large scope:** approximately 205,000 lines across `src`, including roughly 313 C files, 194 headers, and 41 assembly files in source/include/RSP paths.
- **ABI and pointer risk:** 32-bit N64 pointers, segmented addresses, physical-address macros, fixed-point matrices, and `uintptr_t` display-list words are pervasive.
- **MIPS assembly:** 39 assembly files include boot code, RSP/RDP microcode, libultra OS primitives, math, cache/TLB, and random helpers; none can execute natively on Apple Silicon.
- **Raster semantics:** N64 texture tiles/TMEM, TLUT formats, two-cycle combiners, coverage/alpha compare, fog, depth, and render modes require careful semantic matching rather than simple API translation.
- **Asset coupling:** many model/level/audio binaries are ROM-derived. The native loader needs a deterministic extracted-asset manifest and must not depend on N64 physical addresses.
- **Timing/threading:** gameplay assumes retrace-driven queues and N64 cycle timing. Reproducing behavior requires a deliberate host tick model.
- **Reference gap:** without emulator/GPU captures, initial visual acceptance will be weaker until reference artifacts are collected.
- **Audio:** N64 libaudio and sequence/sample formats are a separate port and should not be allowed to block first rendering.
- **ROM/legal boundary:** the external ROM is user-provided and must remain outside the repository and distribution artifacts.
